= Documenting
:toc: left
:toclevels: 2
:sectnums:
:experimental:

How projects write their manuals: AsciiDoc pages put together into books,
rendered to standalone HTML by `tools/doc.sh`, with extensions (plugins) for
what plain AsciiDoc cannot do.

== Rendering

[source,shell]
----
tools/doc.sh doc/developer-manual.adoc              # into build/doc of the project
tools/doc.sh -o /tmp/doc doc/finance/compound.adoc  # elsewhere
tools/doc.sh -a sectnums! doc/documenting.adoc      # with a document attribute changed
tools/doc.sh --help
----

Each `FILE.adoc` becomes `FILE.html` in the output directory, so manuals rendered together can link
to each other with `+link:other.html[]+`. The pages are self-contained: the theme and the scripts of
the extensions are inlined, only the fonts come from the web.

[cols="2,5",options=header]
|===
| Option or variable | Effect

| `-o`, `--out DIR` | Output directory; default: `build/doc` of the project root.
| `-r`, `--require FILE.rb` | An extra extension, for every document of the run. Repeatable.
| `-a`, `--attribute NAME=VALUE` | A document attribute, over the one in the document. Repeatable.
| `ADOC_CSS` | The theme stylesheet; default: `res/adoc/theme.css` of Nexus.
| `ADOC_ROOT` | The project root, which extensions resolve paths against; default: the git root
of the working directory.
|===

== Book style

A project has a few manuals, one per audience: a user guide for those who use the code, a developer
manual for those who change it.

=== The manual is a spine

The manual file holds the settings of the book, a short introduction, links to the other manuals
and the includes of its pages. It does not hold the content itself:

[source,asciidoc]
----
= Project Manual
:doctype: book
:toc: left
:toclevels: 2
:experimental:
:sectnums:

A short introduction.

\include::user-guide.adoc[leveloffset=+1]
\include::dev-guide.adoc[leveloffset=+1]
\include::appendix.adoc[leveloffset=+1]
----

`doctype: book` lets the level-1 sections (parts and chapters) carry the structure, `sectnums`
numbers them for references in reviews and discussions, `toc: left` keeps the outline beside the
text, and `experimental` turns on `kbd:[...]` and the other UI macros.

=== One page per topic

When multiple topics or concepts are described in one section, it can be
further split into subpages. In this case a page is a file with a single topic
and its own level-0 title, as if it were a document of its own. The include
shifts it into place with `leveloffset=+1`, so a page never needs to know how
deep it sits.

[source,asciidoc]
----
= User Guide

\include::ug-module1.adoc[leveloffset=+1]
\include::ug-module2.adoc[leveloffset=+1]
\include::ug-moduleN.adoc[leveloffset=+1]
----

The file names tell the part: `ug-` for the user guide, `dg-` for the developer guide.

=== Pages that also render alone

Some pages are useful on their own, a palette or a style specimen for example. A page renders
standalone when it brings the settings the spine would give, only when it is the document itself:

[source,asciidoc]
----
= Color Palette
\ifeval::["{docname}" == "palette"]
:toc: left
:toclevels: 2
\endif::[]
----

Content that only makes sense in the browser (an interactive page) goes between
`ifdef::backend-html5[]` and `endif::[]`.

== Plugins

What plain AsciiDoc cannot do comes from Asciidoctor extensions, Ruby files that register
processors when they are required. There are three places for them, from the narrowest:

Companion of a document:: `FILE.rb` next to `FILE.adoc`. `tools/doc.sh` loads it for that document
only. Use it for what a single document needs, like the model of its interactive chart.

Project extension:: A file the project passes with `-r`. Use it for what the
manuals of one project share.

Shared extension:: A file in `tools/asciidoc/`, loaded by `extensions.rb` for every document. Use
it for what every project can use; it must not know about any one document or project.

Start narrow and move a plugin up when a second user appears.

=== Writing one

A plugin is a processor class and its registration. The kinds used so far:

[cols="2,3,3",options=header]
|===
| Processor | In the document | For

| `BlockMacroProcessor` | `name::target[attrs]` on its own line | Content built from elsewhere:
tables from headers, boards from sources, charts.
| `BlockProcessor` | `[name,...]` above a delimited block | Content written in a notation of its
own.
| `InlineMacroProcessor` | `name:target[attrs]` in a sentence | A computed value or an icon in the
text.
| `DocinfoProcessor` | Nothing | Styles in `<head>`, scripts at the end of `<body>`.
|===

[source,ruby]
----
require 'asciidoctor'
require 'asciidoctor/extensions'

module Project
  # `todos::[dirs="src,tools"]`
  class TodosMacro < Asciidoctor::Extensions::BlockMacroProcessor
    use_dsl
    named :todos

    def process(parent, _target, attrs)
      rows = scan(attrs.fetch('dirs', 'src'))
      parse_content(parent, table(rows)) # AsciiDoc source, converted like the rest
      nil
    end
  end
end

Asciidoctor::Extensions.register do
  block_macro Project::TodosMacro
end
----

Some rules that kept the plugins simple:

* *Return AsciiDoc where possible.* `parse_content` with generated AsciiDoc gets the theme, the
  numbering and the cross-references for free. Raw HTML (`create_pass_block`) is for what AsciiDoc
  cannot express, like SVG or inputs.
* *Resolve paths against `ENV['ADOC_ROOT']`*, not against the plugin's own location, so the plugin
  works for any project.
* *Fail loudly with the target in the message.* An unknown target raises `ArgumentError`; a
  questionable input logs a warning through `logger.warn`. Both show up in the output of
  `tools/doc.sh`.
* *Mark the documents that need assets.* A docinfo processor runs for every document; inline the
  styles and scripts only where a block is used. The attributes of the body are reset before the
  conversion, so keep the mark outside them (Nexus uses an `ObjectSpace::WeakMap` keyed by the
  document).
* *Safe mode stays on.* `tools/doc.sh` renders in `safe` mode, which allows includes and inline
  content from the document tree, but not writing outside it.

=== Interactive blocks

`tools/asciidoc/interactive.rb` gives a document panels of inputs over a chart, computed in the
browser. The block is generic; a model makes it concrete. Here is a toy one, the line
`y = a·x + b`:

.The line y = a·x + b. Change a and b, or duplicate the panel to compare.
interactive::line[a=1,b=2]

"Duplicate" copies a panel with its current values, so variants (A, B, ...) can be compared on the
same scale. The model takes two files next to the document. The companion, `documenting.rb` here,

starting values:

[source,asciidoc]

----

A companion belongs to the rendered document. When a page with an interactive block is included
into a manual, the manual needs the model: pass the companion with `-r`, or make it the manual's
companion.

== Best practices for writing documentation

* *Prose first, then the reference.* A chapter explains the idea in a few paragraphs before the
  tables and the API.
* *Every figure and table has a title.* The title becomes the numbered caption that the text can
  point to.
* *Link, do not repeat.* A rule lives in one page; the others link to it, across manuals with
  `+link:other.html#anchor[]+`.
* *Generated content stays generated.* If a number can be measured or a table read from the code,
  a script or a plugin produces it.
* *Admonitions are rare.* A `NOTE` or `WARNING` in every section stops being read.
